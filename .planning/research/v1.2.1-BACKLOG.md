## Release process

- **Evidence-only ancestor rule (A).** The gate accepts an exact record whose commit is an ancestor of the release commit, when only `release-evidence/**` changed in between.
  - The gates job fetches enough history (fetch-depth 0 or the range).
  - Five tests: the same commit, an evidence-only ancestor, a code or docs change in between, a commit that is not an ancestor, and a shallow clone failing closed.
- **Receipts from the fresh-clone check.** `npm run verify:fresh` runs every check but writes no Jevris receipt, so Jevris's Stop reminder reports all checks as stale even after a passing run. Two options:
  - let verify:fresh import its results as receipts, bound to the commit it verified;
  - have the Stop hook offer to start a background `jevris verify` when receipts are stale. It must never run checks itself or mark anything passed.

## Harnesses and certification

- **Jev advice latency in everyday use.** A diagnostics report measured about 2 s at p95, against the cap at `packages/provider-typesafe/src/trigger-handlers.ts:183` and `packages/core/src/intent-decisions.ts:68`, with fallbacks at the cap. The live suite measured p95 271 to 359 ms. Find out where the time goes (request size, queueing or the sidecar) and bring advice inside the 900 ms budget.

- **Codex subagent routing (K2).** 1.2 ships Codex subagent routing as advice-only, and the gate no longer requires it. RC6 still fails the case on macOS and Linux with SHELL_NOT_SEEN. F found the cause on 2026-09-28:
  - K2 routes to gpt-6-astra. In Codex 0.157.1's bundled catalog, that model is `use_responses_lite: true` and `tool_mode: code_mode_only`, as are every gpt-6-* and gpt-5.6-* model.
  - Codex therefore sends the tools as an `additional_tools` item inside `input`, not as the top-level `tools`, and in code mode there is no exec_command. Our stub reads only the top-level `tools`, so it answered with plain text.
  - Fix options: route K2 to gpt-5.4 (hidden, unified_exec), and/or teach the stub the lite `additional_tools` item. Either way, real Codex routes to code-mode children, and K2 must also cover their hook and approval path.
- **Kilo and OpenCode model listing.** The second listing run changed each harness's main database (`kilo.db`, `opencode.db`). Tell a real write on every start from our own check catching the warm-up's WAL being flushed, for example with a checkpoint between runs or a third run. Then the owner decides.
- **Codex model listing** is refused because it writes real data to its databases (the `-wal` files are not empty). It stays refused unless Codex offers a read-only listing.
- **G-8.** Mark another serving host's weekly window as weekly, beyond what its text says.
- **G-11, the rest.** Antigravity `PERMISSION_DENIED`.
- **C2's launch-side trace** for a host run with no access scope.

## Usability

- **`jevris verify profile --write`.** Save the proposed checks as `jevris.checks.json` for the person to review, then `jevris verify approve`. Today profile only prints the proposal, and `approve --proposal` approves it without a file.
- **The shared git index.** The index can drift from HEAD, as with `docs/harnesses/parity-matrix.md` on 2026-09-28. A plain `git commit` from outside the agreed process (6e8e0bf3) then commits whatever is staged. Consider a pre-commit hook in this repository that refuses commits not made through `scripts/safe-commit.mjs`.

## Robustness

- **A killed sidecar reported as running in a container with no init.** Found by F in the Linux Docker run. A `sleep` running as PID 1 never reaps children, so a killed sidecar stays a zombie and `kill(pid, 0)` still reports it alive. Three operations drills failed that way until the container ran with `--init`. Treat process state Z as stopped.
- **Flaky test P12.** "decision.feedback records a reasoned rejection of a known decision, the latest wins, and cost.report reports it without changing a policy" failed once in the shared checkout on 2026-09-28 and passed on the next run.
- **`scripts/docs.mjs` writes on any argument except `--check`.** Running it with `--help` rewrote docs/platform-support.md. Add `--help` and refuse unknown arguments.

## Owned workers (owner decision 2026-09-29: documented for 1.2, fixed in 1.2.1)

- **Certify the real worker launch.** Certify's nine worker cases run each port against a Node stand-in; the real binary is used only for `--help`. The stub cases that do start the real binary (worker.actual-model, access limits) use a simplified command line. Make certify run each harness's real worker port (exact argv, agent and permission config) against the loopback stub with a dummy key, for all five harnesses. Real-model tests exist only for Claude Code and Codex, opt-in and billed.

## Slow hosts and Jev answer quality (found in round 3, 2026-10-05)

- **Two more abandon paths give the engine no late grace.** The route's slice classification had this defect and is fixed (bca5a4b): the engine's deadline equalled the caller's wait, so on a slow disk the abandoned call ended with DEADLINE before it was sent. `packages/core/src/plan-slices.ts` (~line 280) and `packages/provider-typesafe/src/sidecar-ops.ts` (~line 898, `Math.min(2000, remainingMs)`) still do. Give them the same one-second grace and a test, as the other abandon paths have.
- **The Windows cause of the K3 lifecycle-load stall is unproven.** A sidecar loop stall of 1.5 s or more at the first `git` process fits the CI numbers and an injected stall reproduces the signature, but no Windows run has measured it. If it is process creation on the loop thread, `GitPort` spawns could run off the main thread. Needs a Windows run.
- **Windows CI mitigations are unmeasured.** The test budget scale (`JEVRIS_TEST_BUDGET_SCALE`, 6 on Windows under CI) and the Defender exclusion step in `ci.yml` are test and CI only; check the Windows failure rate over the next few runs. Two further options were not applied: `--test-concurrency=2` for the second Windows batch (adds roughly 2 to 4 minutes) and a lower scale.
- **A uniformly slow disk stays red.** A disk slow on every write (1.5 to 3 s) cannot be fixed by asking again or by scaling a budget: a cold decision needs four durable writes. Not a test problem.
- **Per-question confidence floors need a calibration set.** The floors (0.6 confidence, 0.15 margin, 0.6 Noul certainty) are conservative defaults. Score confidence has a median of 0.54 and 48 percent of Score answers clear 0.6, but the answers that clear it were in range 22 of 22 times. A per-question floor needs a labelled set, a holdout and a signed release (spec 2.2, 18.4, 18.5); the live distributions are in `docs/settings.md`.
- **Repeated-failure "which artifact next" has no Jev part.** Measured live: it cleared the floors in 2 of 24 answers even with the failure's first line, so the rules name the artifact. Revisit with a richer feature set (for example the exit code and the failing test name as screened spans) only with a calibration set.
- **C68 and three side-effect actions stay on the raw `capability.advise` op** (worktrees, patches, probes, roots, write branches). Expose them only behind a write-capable tool with its own permission story.
- **Project memory (C24) has no admit command.** Admitting an entry is a provenance and consent question; design it before adding a command.
