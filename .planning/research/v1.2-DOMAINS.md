# Jevris v1.2 domain teams

This file replaces the one-phase-at-a-time runner for phases 28 to 63. Six long-running domain agents work **at the same time on `main` in the main checkout**. There are no worktrees and no branches. Each agent owns a fixed set of files and a fixed set of requirements, and works through its whole backlog.

Everything in `v1.2-PHASE-RUNNER.md` still applies (sources of truth, safety invariants, test-first, cross-platform, no real HOME, no real keychain, no real harness binary in `npm test`, external inputs don't block), **except** the per-phase GSD ceremony. Domain agents do not spawn researcher, plan-checker or verifier subagents, and do not write per-phase CONTEXT, PLAN or SUMMARY files. They keep one status file each.

## Shared files (additive edits only)

- `packages/contracts/`: any domain may **add** a new type file and one export line. Never change an existing contract's shape without messaging the orchestrator first. Then run `schemas` to regenerate and commit the schema files with the change.
- `packages/core/src/index.ts` and each package's `index.ts`: add export lines only.
- `apps/cli/src/cli.ts` (owned by E): another domain may add one dispatch line for its own command. Keep it to that line.
- A package's own `package.json`: its owner may add a dependency. Root lockfile changes happen only while holding the suite lock (below).
- `.planning/REQUIREMENTS.md`, `ROADMAP.md` and `STATE.md`: **orchestrator only.** Domains report through their status file.

When you need a file another domain owns, do not edit it. Code against the `@jevris/contracts` interface with a local fake, list the need under "Needs from other domains" in your status file, and message the orchestrator (`SendMessage` to `main`).

## Dependencies between domains

Build to the contracts, not to another domain's internals. If a dependency hasn't landed yet, write the adapter against the contract, test it with a fake, and wire it for real when `git log` shows the owning domain has landed it. Rough landing order:
- B's sidecar daemon and C's provider land first.
- E's surfaces need both.
- D needs B, C and E.
- F needs E.
- A packages and releases last.
Everyone can start immediately on the parts that don't depend on anyone else.

## Concurrency protocol (mandatory)

1. **Commit only your own paths**: `git add <your paths> && git commit -m "<msg>" -- <your paths>`. Never use `git add -A`, `git add .`, `git commit -a`, `git stash`, `git reset`, `git checkout -- <others>`, rebase, or anything that rewrites history or touches files you don't own. If `index.lock` exists, wait 5 to 30 s and retry.
2. **Suite lock.** Any root `npm run build`, `npm test`, `npm install` or `npm ci`, or lockfile change, runs only while holding the lock directory `.jevris-suite.lock` in the repo root:
   - Acquire it with `mkdir .jevris-suite.lock`, which fails if another agent holds it; wait and retry. Write your domain letter and the time into `.jevris-suite.lock/owner`.
   - Remove it when done, including on failure.
   - A lock older than 30 minutes is stale and may be removed.
3. **Between suite runs**, test only your own compiled tests: `node --test <your package>/test/*.test.mjs` after a build under the lock.
4. **Before each commit**, run the full `npm test` under the lock.
   - If only your own tests fail, fix them before committing.
   - If a failure is in another domain's files and your change didn't cause it, you may still commit your own paths. Record the failure in your status file and message `main`.
   - Never commit a change that breaks another domain's tests.
5. Commit messages use conventional format with the domain in the scope, e.g. `feat(B/sidecar): ...`. Every message ends with:
   `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`
   Do not push, and do not publish.

## Status file

Each domain keeps `.planning/domains/<letter>-<slug>/STATUS.md`:
- a checklist of every owned requirement ID: `[ ]` open, `[x]` done with test evidence (test file:name) and commit hash, `[~]` done pending external evidence with the named single command
- decisions made
- needs from other domains
- known failures

Update it with each commit. The orchestrator folds it into REQUIREMENTS, ROADMAP and STATE.

## Token discipline

- Read only the SSOT sections and audit rows your requirements cite. Don't reread whole files you have already read.
- Don't spawn subagents.
- Keep test output short: summaries, and on failure only the failing test's name and assertion.
- Batch related requirements into large commits, each a coherent vertical slice with its tests.

## Definition of done (owner directive, 2026-09-25)

A domain agent must NOT finish, hand back or stop until its **entire** domain is production-ready. When all six domains finish, the complete Jevris platform must be built and ready for production. Before your final reply, all of these must be true:

1. **Every requirement is closed.** Every requirement ID your domain owns is `[x]`, with a named test and a commit. A requirement may be `[~]` only when its sole missing piece is an input that cannot exist on this machine (see `v1.2-EXTERNAL-INPUTS.md`), and then:
   - the code path is complete;
   - it is proven with fakes, fixtures or contract tests;
   - it has a named single command that produces the live evidence.

   "Unsupported", "abstain", "not-a-pass", TODO or stub behaviour is not done where the SSOT specifies behaviour.
2. **Every item is integrated.** Each SSOT capability, workflow and user story mapped to your requirements runs through the real product path (installed CLI, sidecar, MCP, hooks or harness plugin as applicable), not only at library level, and an end-to-end test proves it.
3. **Every dependency is wired.** Everything you built against a fake while waiting for another domain is wired to the real implementation, once it has landed, and is tested. If another domain has not landed something you need, keep working on everything else. Check `git log` periodically. Do not finish until the need is met, or the orchestrator explicitly releases you.
4. **The suite is green.** The full `npm test` passes on the final main under the suite lock, with no skipped or todo tests in your area.
5. **It runs on every platform.** Your code paths have Windows, macOS and Linux coverage: real, or injected-platform unit tests plus CI matrix entries. They also work on Node `^22.14.0 || >=23.6.0`.
6. **The production checks pass.** Security review of your area:
   - no secret in logs or argv;
   - no model-callable destructive action;
   - no write outside owned paths;
   - timeouts and bounded resources;
   - error messages that tell the user what to do.

   Your area also has user docs, which domain A integrates.
7. **The status file is complete.** Your `STATUS.md` shows every requirement with its evidence, and a final "Production readiness" section confirms points 1 to 6.

If your context grows large, keep going. It is compacted automatically. Do not hand back early to save context.

### 2026-09-30: Owner decision: an opt-in setting queues missing checks at Stop

- **Owner approved (2026-09-30).** A new setting, `verification.backgroundAtStop`, values `off` (the default) and `on`. When it is on, a main-session Stop that finds approved checks missing or stale queues those checks in the background, through the same scheduler as `jevris verify`. The Stop never blocks and never waits: the next Stop or session finds the receipts.
- **Rule.**
  - Only approved checks from the current approval record, and only those missing or stale by the existing freshness rules. Nothing runs when nothing is missing.
  - Only a main-session Stop, never a subagent's. Jevris must be on, the mode must allow acting (bounded-auto), and the kill switch must be clear.
  - One queued run per workspace: a request joins or queues behind a run already under way, exactly as `jevris verify` does.
  - Debounce: no new run while a run for the same checks is running or queued, and none after a background run for the same checks at the same input revision produced a failing receipt. A new input revision may queue again.
  - The Stop answer keeps its shape and its single reminder rules. The report says the checks were queued ("Still running in the background: ...").
  - Receipts are ordinary receipts with the same independence and freshness rules. Only the runner marks anything passed.
- **Authority.** A repository file is not consent. Only your own file may turn it on, through `jevris configure set verification.backgroundAtStop on`, which needs a person at an interactive terminal like the other raises. The workspace `.jevris/config.json` may only turn it off; an `on` there is ignored.
- **Why.** The Stop reminder asks the model to run checks that Jevris can run itself, and the model often ends the turn instead. Queuing them in the background costs no model tokens and leaves the next Stop with fresh evidence, with permissions and verification unchanged.
- **Spec.** This extends the spec's Stop behaviour (line 706, "a Stop only requests missing evidence") as an opt-in actuation. The spec text stays unchanged; `ssot_docs/` is not edited. With the setting off, Stop behaves exactly as before.
