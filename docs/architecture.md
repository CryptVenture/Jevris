# Architecture

Jevris keeps what must be deterministic out of the coding model. Facts, arithmetic, permissions and verification are ordinary software. Jev is asked only bounded questions. The coding model keeps writing the code, and the harness keeps deciding what a tool may do.

## Authority

| Kind | Who decides | How far it goes |
| --- | --- | --- |
| Observe | Jevris records what the harness did | On where Jevris is installed, unless the mode is `off` |
| Advise | Rules first; Jev only for a bounded question | Shown from mode `advise` up; never applied by itself |
| Actuate | A certified hook, runner or owned worker | Only in mode `bounded-auto` (the default), and only where a signed certification record covers the harness, its version and the OS; still under native permissions |

The `mode` setting (`off`, `observe`, `advise` or `bounded-auto`) is the single ceiling on all three. Other settings, host and organization policy can only lower it, and raising it needs a person at an interactive terminal. See [settings.md](settings.md#modes).

Native permissions and the sandbox stay authoritative. On a certified hook Jevris can add context. It can also choose a subagent's model (`hooks.route`) on Claude Code, Codex, Kilo and OpenCode, each only after that harness's own certification. The 1.2 release does not require it on Codex: there it routes only where its certify case passes on the installed version, and advises otherwise. On Claude Code it does so for a low-risk launch (a read-only built-in by the rules; a write-capable type is high by the rules and only one bounded Jev answer at the floors lowers it) or with evidence for that subagent type (an active learned slice or a signed prior), for that one Agent call only: the session's model is never changed. On Codex, Kilo and OpenCode it does so only with that evidence. It never overrides an explicit model or a pin. The sidecar receives only the subagent type, the size of the tool input and the names of its keys, never the prompt or the description. It returns a model id, which Claude Code maps to `haiku`, `sonnet`, `opus` or `fable` (with a short note for the model), and the other harnesses receive in their own spelling. Antigravity gets the advice as text only (see [routing.md](routing.md#subagent-routes)). Subagent outcomes do not feed learning yet and 1.2 ships no signed prior, so on Codex, Kilo and OpenCode it abstains in practice. Jevris never grants a tool, widens a sandbox, answers a permission prompt or writes a permission decision. Uncertified means observe only, and any failure (a late or missing sidecar, a refused frame) falls back to observe.

Certification records cover a harness version range, not one version, so a routine harness upgrade needs no manual step. Real use adds live evidence: each hook delivery the sidecar records, and each owned worker's first-use check, counts as conforming or malformed for one feature at one harness version (names and counts only, never content). A malformed one demotes that feature at once. `jevris doctor`, the sidecar's start and each SessionStart start a re-check in the background for a version outside every record's range, a demoted feature, or a record that predates a feature (`worker.route`): `jevris certify` in a throwaway profile, with no model call, at most once per version or demotion. A pass writes a record that covers the new version. Observation and advice never wait for it; only actuation of the features not yet covered does. The `worker.route` feature certifies how owned workers are routed (model and effort), "certified pending first use": certify checks the flags and the worker port with no model call, and the first real run checks its init before any tool runs. In 1.2 it does not gate starting a worker, and certify runs the port against a stand-in, not the real harness ([routing.md](routing.md#what-certification-covers-for-owned-workers-in-12)). See [harnesses/parity-matrix.md](harnesses/parity-matrix.md#how-to-read-it-on-your-machine).

## Processes

```text
 coding harness (Claude Code, Kilocode, Codex, OpenCode, Antigravity)
   |  hook event (stdin JSON)          |  MCP tool call (stdio)
   v                                   v
 hook launcher                       MCP server
 dist/hook.mjs, closed bundle        plugins/shared/mcp.js
   |  authenticated frame              |  runs the jevris CLI, arguments on stdin
   v                                   v
 sidecar  <---------------------------- jevris CLI
 dist/sidecar.mjs                     dist/cli.mjs
   |  decision engine, budgets, store, orchestrator
   |  the only process that reads the Jev key
   v
 Jev API (only with a key, within budget, and only with administrator consent for source)
```

- **Hook launcher.** Starts on every harness event, reads the event, asks the sidecar within the harness's hook deadline and prints the answer the harness expects. Its import graph has no store, SDK or keychain, so it starts fast. Late, missing or refused means "observe".
- **MCP server.** Exposes 17 tools. Each call runs the installed `jevris` command with the arguments on standard input; administration (install, settings, credentials, kill switch, policy, data deletion) is not reachable through MCP. See [mcp.md](mcp.md).
- **CLI.** The public commands, administration and operator tools. Commands start the sidecar on demand and fall back to a reduced, local answer that says so.
- **Sidecar.** One per user. Listens on a Unix socket, or a per-user named pipe on Windows, in an owner-only runtime folder, and authenticates every frame with a per-boot key in an owner-only file. It owns the decision store, the decision engine, budgets, route learning and the orchestrator. Lifecycle: hooks, commands and MCP tools start it on demand, and it exits when idle. When a service is installed for the home, an on-demand start asks the service manager to start the unit instead of spawning a second sidecar (a hook waits at most a moment for the manager, then answers rules-only; if the manager refuses or cannot be reached, the sidecar is started on demand, unless the service's own sidecar is alive but not answering). Install, and `jevris service install`, hand a sidecar that runs on demand over to the service by asking it to stop (the graceful shutdown request), so one sidecar remains. A reinstall replaces the runtime under it, so install asks a running sidecar on an older build to stop with the graceful shutdown request (in-flight requests drain first) and starts the installed build at once on the same endpoint, and the first hooks after the install are answered. A sidecar that was not running is not started, and neither is one when `JEVRIS_SIDECAR_AUTOSTART=0` is set. A supervised sidecar (`jevris service install`) is never started next to its service: it retires itself when its build is stale and it is idle (no connection, no request in flight, no verification run under way) and its service manager restarts it. `jevris sidecar restart` and `start` reach a supervised sidecar through its service manager (launchd, systemd or Task Scheduler), never by spawning an unsupervised one, because the manager does not restart a clean exit; when the manager cannot be reached the restart refuses with `SERVICE_UNREACHABLE` and stops nothing. A sidecar the service runs that is alive but not answering is still the service's here: a `start` the manager refuses or cannot take starts nothing beside it and fails with `SERVICE_START_REFUSED` or `SERVICE_UNREACHABLE`, as it does for a hook, a command and an MCP call, and a `restart` of it gives the same refusal, naming the pid, and stops nothing: a sidecar that does not answer cannot be asked to stop, so the stop would be a signal that its shutdown guard never sees, and the manager is asked to start the unit first (a start leaves a running unit running). Only a manager that takes the start is followed by the stop and a second start (a manager that accepts and brings nothing up ends in `SERVICE_START_TIMEOUT`, as for `start`), and `jevris sidecar restart --force` orders the stop anyway, without that question. The sidecar decides whether a stop may happen: while it is finishing a verification run it refuses (`VERIFICATION_RUNNING`) and keeps running, and only `jevris sidecar stop --force` overrides that; install never forces it. A stop that is accepted closes the socket, waits for a verification run that began after it was accepted (a graceful `shutdown` only), closes the state, then removes the endpoint, pid, locality and key files and its socket, and releases the daemon lock, in that order, so a `jevris doctor` that finds an endpoint file with no live process is looking at a crash, not at a stop in progress. Closing the state ends the store's maintenance worker thread, and never inside its load of the SQLite addon (`apps/sidecar/src/maintenance.ts`, "the native load"): a thread ended there aborts the whole process with SIGABRT before the files are removed, so a stop that finds the worker loading waits for it, at most 5 s. Four more worker threads, started once the sidecar is up and ended after five idle minutes, start every `git` process the sidecar runs (the revision for a capsule, a restore, a Stop reminder and a handoff): starting a process blocks the thread that starts it, which on Windows is seconds on a loaded host, and four sessions compacting together stood the single event loop still for the sum of four starts (`packages/orchestrator/src/verify/git-work.ts`). A git call before a worker is ready, with no pool, or after a worker fails or ends, runs in the calling thread as it always did. A promise that is rejected with no handler stops the sidecar the way a signal does, not the way Node's default does (`apps/sidecar/src/daemon.ts`, `runSidecarMain`): the log names the reason code `UNHANDLED_REJECTION`, the stop removes the files, and the exit code is 70. It never keeps serving, because what the rejected work was doing is unknown. A worker run that throws is handled earlier, in `runLeasedTask` (`packages/orchestrator/src/orchestration/workers.ts`): it is a failed run with an unknown cost, and the queue behind it starts. A restart that fails never fails the install; one line gives the reason code and the fix.
- **Owned workers.** For owned work, the orchestrator starts an installed harness headlessly, one leased task per run in its own git worktree, under your subscription login or an API key. All five harnesses can run one. Route learning may choose the model and effort only on a harness certified for `worker.route`; elsewhere it advises. The Claude Agent SDK runs only with an API key. See [routing.md](routing.md#owned-workers).

## Where Jev is asked

Every place the product can ask Jev is listed in one inventory (`FEATURE_INVENTORY` in `packages/provider-typesafe/src/features-inventory.ts`), and a test (`features-inventory.test.mjs`) keeps the list, the source and the docs in step. Each entry has one implementation, a wiring class and a named real entry: a hook event, a command, a tool or an op. The test fails when a file or consult site that asks Jev is missing from the list, when an entry is `dormant` (the code exists and nothing supplies what it needs) or `not-asked`, and when a capability has no command, tool or op that reaches it. A decision that nothing reaches is a build failure, not a quiet gap.

Every one of them is advice only. Rules answer first; Jev is asked only where the rules are not sure, at the same floors (a confidence of 0.6, and 0.15 between the best two options of a Choice), under the mode, the kill switch, `jev.assist`, the budgets, the circuit and the 12-question cap. A miss, a late answer or an unsafe one falls back to the rules, with a reason code. With source egress not approved, a decision sends content-free features only, or is not asked at all (see [privacy.md](privacy.md)).

| Wiring | Count | Where it runs |
| --- | --- | --- |
| Hot | 7 | Inside a hook or op a person waits for, with a Jev wait of at most 700 ms (the 900 ms hot budget less 200 ms, whatever budget class the request asked for: a hook has the hot budget, and `jevris route` and an MCP tool call ask for the 5 s background budget, but their wait for Jev is still the hot budget's): the task slice (`jevris route`, `jevris plan`), the check ranking (the Stop hook, `jevris verify`), the health probe, the compaction audit (C20, on `PostCompact`), the capsule pick (C21, on `SessionStart` resume) the project-memory rescore (C24, on the `SessionStart` restore) and the risk of a Claude Code subagent launch (on `PreToolUse` for an Agent call; the wait is the time left less 300 ms, at most 700 ms). |
| Detached | 10 | After the hook or op has answered; the line waits for the session's next event and nothing waits on it: repeated failure (the same-failure question; which evidence comes next is the rules' pick and C05 asks Jev nothing), new task (the task family C01, the open point C02 and the template C04), scope change (C06, on the diff boundary), the two security checks (C49, C51), the check-output spans (C22, in `jevris verify`) and the worker-readiness advice at an owned-worker launch. |
| On demand | 37 | Only when an agent or a person calls it: the capability catalogue through `jevris advise <id>` and `jevris_advise`, `jevris delivery` and `jevris_delivery_report`, `jevris plan` with requirements or candidates (C03, C07), `jevris checkpoint` (C18, C19 with `--context-percent`, C23 with `--constraint`) and `jevris recover` (C29). |

Where it is made visible: `jevris explain <decision-id>` shows one advisory record per run (the decisions it asked, what each answered, and the reason code of every miss). That record is the summary of the run and makes no provider call of its own, so its Provider line says that Jev was asked and that each question is its own decision record, which shows the model and the usage (or that the decision cache answered, or, for a run that never asked, that no provider call was made); the usage is counted once, on those records. The worker-readiness advice is also in the task view (`readiness` on `task.get`, the `jevris_get_task` tool), with the decision id to explain. A new task records one advisory record that names C01, C02 and C04.

Thirteen of the capabilities that no command named are reached through the existing `jevris advise <id>` command and the `jevris_advise` tool by capability id, with a fixed input shape each (decision of 4 October 2026): C32 to C38, C40, C62, C67, C69, C70 and C72. No new command and no new tool was added; the MCP surface stays at 17 tools. Each takes only its own input keys, refuses an oversize or unknown input before anything runs, prints plain text like the others, asks Jev about text you give it only with source egress approved (the table in [privacy.md](privacy.md#what-each-capability-asks-with-egress-denied) says which capabilities ask with it denied; the others answer from the rules with no request and no decision), and records a decision when it asks. The fourteenth, C68 (safe speculative evaluation), stays on the raw `capability.advise` sidecar op on purpose: it creates and removes git worktrees and applies candidate patches in them, which a tool that is read-only advice must not do. Some actions of the exposed ones stay on the raw op for the same reason: C32's bridge probes, C33's extra skill roots and C67's proposal branch. The inventory names C68 and says why, and its test lists it.

Two entries are inert until something supplies their input, and the inventory says so rather than hiding it. The project-memory rescore (C24) asks nothing until entries have been admitted, and no command admits one in 1.2.0, on purpose (decision of 4 October 2026): `admitProjectMemory` takes an entry only when passing receipts or a named person vouch for it, and admitting an entry is a question of provenance and consent. A repository file is not consent, and an agent's own claim is not a receipt, so a command that lets one in needs its own design, with who may admit, what is shown first and how an entry is withdrawn; until then project memory stays empty and the restore carries none. The compaction audit (C20) needs the compaction summary, which only a harness whose `PostCompact` event carries it sends (Claude Code does).

## Packages

All workspaces are private and bundled into the one published package.

| Package | Role |
| --- | --- |
| `@jevris/contracts` | Types and runtime schemas for every boundary (CLI, MCP, sidecar frames, hooks, evidence). No I/O. |
| `@jevris/platform` | Per-OS paths, process spawning, atomic writes, path identity and owner-only permissions. |
| `@jevris/core` | Rules, egress, the decision engine's pure parts, packets and redaction, advice, the model registry, the router and route learning, checkpoint, shortlist. No store or native addon at load. |
| `@jevris/store` | SQLite store (better-sqlite3): migrations, decisions, tasks, receipts, audit, backups. |
| `@jevris/provider-typesafe` | The only production Jev transport (`@typesafe-ai/sdk`), budgets and the sidecar decision engine. The transport owns each call's total deadline: connect, headers and the body read all end at it, even when the network or the SDK stalls, and a late call is `DEADLINE`. It sends over `node:https` with a small keep-alive pool, one socket per concurrent request, not over Node's global `fetch`: measured live, the global fetch ran four parallel requests to the API one after another (201, 389, 573 and 776 ms) where separate sockets all took about 240 ms. The sidecar sends its requests through that pool (the egress guard wraps it), keeps an idle connection for 30 s (the API keeps one for at least 120 s) and drops one a sleeping machine left half open. When it starts, and only if Jev could be asked right now (a key, a mode that allows background network work, `jev.assist` not off, the kill switch clear), it opens the connection (TCP and TLS; no request and no data), and it compiles the decision path's validators, so the first request pays for neither. |
| `@jevris/orchestrator` | Task graphs, leases, reservations, owned workers and their harness and auth choice, verification runner and receipts, settings, memory capsules. |
| `@jevris/evals` | Evaluation protocol, corpus, holdout and review records. |
| `@jevris/languages` | Manifest-based workspace profiling and check proposals. |
| `@jevris/mcp` | The MCP server, emitted as `plugins/shared/mcp.js`. Every harness runs this one file. |
| `@jevris/adapter-*` | One per harness: its hook protocol, config files, install and doctor probes. `adapter-claude-sdk` drives owned Claude sessions through the optional Agent SDK, with an API key only. |
| `apps/cli`, `apps/sidecar`, `apps/hook` | The three programs above. `apps/cli` also holds install, doctor, certification and the owned-worker drivers for each harness CLI. |

## What stays local

Everything, by default: the store, logs, receipts, capsules, route learning and packs live in the Jevris data folder under your home, readable only by you. A Jev call sends only a bounded question and the evidence an administrator approved for egress; source is never sent without that consent. Remote telemetry is off. See [privacy.md](privacy.md) and [security.md](security.md).

## Distribution

One npm package, `@webventures/jevris`. `install` copies its runtime to `<data>/runtime/<version>/` and points every harness there, so nothing runs from the npm cache and no hook calls `npx`. See [installation.md](installation.md).
