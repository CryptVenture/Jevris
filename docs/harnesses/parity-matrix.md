# Jevris harness parity matrix

This matrix covers each feature in each of the five supported harnesses. Every cell is
either implemented or unsupported. An unsupported cell gives its reason, and `jevris doctor`
prints it on that harness's `parity` line.

The source for the rows is each harness's own manifest, `plugins/<harness>/harness.json`:
- `hooks`: the registered hooks.
- `events`: the forwarded bus events.
- `features`: what `jevris certify` can prove.
- `unsupported`: every missing feature, with its reason.

`apps/cli/test/harness-manifests.test.mjs` fails if a manifest drifts from its adapter.

Antigravity is three products: the Antigravity CLI (`agy`), the Antigravity app and the
Antigravity IDE. All three load the Jevris plugin from `~/.gemini/config/plugins/jevris`, so the
Antigravity column applies to each of them. Only the CLI can be certified headlessly.

**Which models the routing features cover.** The bundled model registry (`multi-2026-10-08`) lists seven providers: Anthropic, OpenAI, Google, xAI, Z.ai, Moonshot and DeepSeek. So model routing, account eligibility and cost per task cover all of them, in every harness that reaches the provider: Claude Code for Anthropic, Codex for OpenAI, Antigravity for Google, and OpenCode and Kilo for each provider through a provider configuration. Each harness has its own baseline: Sonnet 5.5 on Claude Code (Opus 5.5 until 8 October 2026), GPT-6.1 Sol on Codex and Gemini 3.8 Flash on Antigravity. Kilo and OpenCode use the session's own model and provider; only a session model Jevris does not know falls back to the registry-wide baseline, now Sonnet 5.5. The non-Anthropic models are unevaluated, so learning explores one only with evidence (a qualified board prior or outcomes) and only on a low-risk task, and switches to it only after 12 local outcomes per arm, and a model is eligible on a harness only from local evidence. Kimi and DeepSeek models need that provider's consent (`jevris consent provider`), and a preview model never enters an automated route. Any model still gets observation and verification, and its checks and receipts count the same way. Owned workers run all seven providers' models; GLM, Kimi and DeepSeek workers run in OpenCode or Kilo, and a Kimi or DeepSeek worker is refused (`PROVIDER_CONSENT_REQUIRED`) until that provider's consent is granted. An administrator can replace the registry with an unsigned `model-registry.json` in the Jevris config folder, which is validated against the registry schema. See [routing.md](../routing.md).

Decision inputs go to the local sidecar next to the event, as `body.task`, `body.scope` and `body.evidence`. They are never recorded in the event log. The task is the prompt text, clipped to 4000 characters. Scope is the written paths only, relative to the working directory, and never file content. Evidence is the error's first line, clipped to 300 characters. The approved scope comes from the task's plan in the sidecar, not from the harness. No harness reports which effect a native approval prompt approved, so no approval is taken from a hook.

### Subagents

A subagent is one the harness starts itself: Claude Code's Agent (Task) tool, Codex's
`spawn_agent`, the `task` tool in Kilo and OpenCode, and Antigravity's `invoke_subagent`.
- Jevris makes no permission decision in any harness, in a session or in a subagent, with one exception: a certified Codex route answers `allow` on the `spawn_agent` call it rewrites, because Codex applies `updatedInput` only with `allow`. The harness's native permissions are the control in a subagent, and certify's `codex.subagent-route` case checks that they still apply there.
- The verification gate answers only the parent's Stop, in Claude Code, Codex and Antigravity (through its Stop `continue`, on the first stop of a run only). A subagent's stop is never held. Kilo and OpenCode have no stop gate yet: continuing on idle through the plugin client is not built.
- Every adapter reports a subagent's event the same way: under the parent session, with `agentId` naming the subagent and `parentSessionId` naming the parent. A subagent's start, prompt, stop, compaction and end become worker events, so they are never the parent's task, turn or session end. The sidecar records no model for the session from a subagent's event.
- Certify proves a subagent route without a billed model turn: its stub cases run a real turn in the throwaway profile against a loopback stub provider with a dummy key, so no provider is called. Codex's `hooks.route` is certified only when `codex.subagent-route` passes, and Kilo's and OpenCode's `hooks.route` and `session.route` only when their `subagent-route` and `session-route` cases pass; `claude.subagent-route` reports without gating. Codex's, Kilo's and OpenCode's `worker.actual-model` (an owned run's own hooks report the model its request carried) is certified only when the installed hooks run and `<harness>.worker-actual-model` passes. The Codex case has not passed on Codex 0.157.1 in the maintainer's certify runs of 28 September 2026 (first `NO_SPAWN_TOOL`, then `SHELL_NOT_SEEN`), so Codex's `hooks.route` is not certified there and its routes are shown as text. 1.2 does not require Codex subagent routing for release; Codex routes subagents only where its `codex.subagent-route` case certifies on the installed version, otherwise it advises. Antigravity has no custom endpoint, so it has no stub case. The rest of the Subagents row (which hooks fire in a subagent, and what it inherits) is not certified (c).

Coverage key for the Subagents row:
- **a**: the vendor documents it, or its source shows it at a pinned tag (Codex rust-v0.157.1, OpenCode v1.18.32, Kilo v7.8.1).
- **b**: a Jevris fixture or test covers it (`packages/adapter-codex/test/subagent-events.test.mjs`).
- **c**: certified on the installed binary.
- **live**: seen in a real Jevris store, but not certified.

## Model listing

The sidecar keeps a per-machine list of the models each installed harness offers to its current sign-in, so the router can tell which models this account can use. It runs only while the sidecar is idle, never from a hook, one harness at a time.

| Harness | Command | What counts |
| --- | --- | --- |
| Claude Code | an idle `claude -p --input-format stream-json`, sent only the `initialize` control request; no user message, so no model runs | the model list in the answer; the account part is never read |
| Codex | `codex -c check_for_update_on_startup=false app-server`, then `initialize` and `model/list` over stdio | each visible model's `model` id; hidden models are left out |
| OpenCode | `opencode models` (never `--refresh`), with `OPENCODE_DISABLE_AUTOUPDATE=1` | a `provider/model` line whose provider is the one the owned worker would use for that model; the id without its provider. A line through a pinned serving host (`openrouter/moonshotai/kimi-k3`) counts only when the registry has that exact serving for the harness, and the listing keeps the line's own spelling and host. An unpinned host, a `:free` or a `~` line stays out |
| Kilo | `kilo models` (never `--refresh`), with `KILO_DISABLE_AUTOUPDATE=1` and `KILO_NO_DAEMON=1` | as OpenCode |
| Antigravity | `agy models` | one id per line |

- **Certification.** A listing runs only when a signed record certifies `models.list` for the harness version and OS. The certify case runs the listing twice in the throwaway profile. The first run is a warm-up, because a fresh profile's first-run setup (an installation id, bundled skills, a new database) is not a listing effect. The profile is snapshotted before and after the second run. Between the two runs, certify folds every SQLite write-ahead log in the throwaway profile into its database (`wal_checkpoint(TRUNCATE)` through the bundled better-sqlite3; only there, never in your own profile, and no row is read). A harness that is killed when its listing ends never checkpoints, and the next clean close would otherwise show the warm-up's frames as a change of the second run. After the fold, a `.db` that changes, or a `-wal` that holds data, on the second run holds a write of that run and fails it. If the driver cannot load, the fold is skipped and the check is as strict as before. Any write on that run outside caches and logs (a session, history, config or database) fails it with `LISTING_SIDE_EFFECT`, except Kilo's and OpenCode's own `<h>.db-shm`, and their `<h>.db-wal` when it is empty or gone afterwards (the `.db` itself must not change, and a non-empty `-wal` holds a write) Claude Code's `.claude/sessions/<pid>.json` and `<pid>.*.key` for the listing process's own pid (the warm-up run's entries only when they are gone afterwards, and `.claude/plugins/known_marketplaces.json.lock` only when it is empty or gone), and, directly in Codex's `.codex` folder, a SQLite database's `-shm`, its `-wal` when it is empty or gone afterwards (a main `.sqlite` file must not change), the log database `logs_<n>.sqlite` and its side files, and the temporary folder `.tmp`. An updater or version-check file on either run fails it with `LISTING_SELF_UPDATE`; Antigravity's listing runs with `AGY_CLI_DISABLE_AUTO_UPDATE=true`, the opt-out its documentation names (only the literal `true` works; `1` does not, agy issue 1046). An updater file still fails it, so a listing that still starts an update stays off. Directly in its `.gemini/antigravity-cli` folder, the second run may also touch a database's `-shm` (and its `-wal` when it is empty or gone afterwards) and the cache of MCP tool descriptors, `mcp/<server>/<tool>.json` and `instructions.md`, except a file whose name suggests a token or a credential. That allowance is needed: `agy models` starts every configured MCP server and refreshes each server's descriptor cache (18 files for Jevris's own server on the recorded run), and Antigravity documents no flag, variable or setting that skips MCP loading for a run (its `disabled` key is per server, and issue 1088 reports print mode ignores it). The sidecar runs the listing at most once every 24 hours, when the installed version changes and when there is no listing yet, while idle, one harness at a time, each bounded to 10 seconds. Codex's per-process helper folder `.codex/tmp/arg0` (the `apply_patch` links, the exec wrapper and a `.lock`, made at every startup) is a temporary folder like `tmp`, so it never counts. The conformance evidence of each certify run records the listing's reason code and the paths its checked run touched, relative to the throwaway profile: at most 64, never a file's contents, and any path that could carry a secret, a URL or an email address is withheld. The touched paths are named, by path only. A failed `models.list` does not fail the harness's certification; only the listing stays off. A record written before `models.list` existed is re-checked once in the background after an upgrade of Jevris: the same throwaway profile, no model call. Claude Code's records never carry it, so they are never re-checked for it. A record that already carries `models.list` as failed (unsupported, with its reason code) is not re-checked automatically, and neither is one that carries it as certified: after a change to the listing rules, run `jevris certify --harness <name>` again by hand. A new harness version outside the record's range does start the background re-check.
- **Bounds.** Each listing has 10 seconds, after which the process tree is killed, and 256 KiB of stdout. At most 512 ids are kept, each checked against the model id pattern, and at most 512 spellings. Output text is never kept.
- **Opt-out.** `jevris configure set routing.modelListing off` stops every listing ([settings.md](../settings.md)).
- **Doctor.** Doctor prints one line per installed harness: `harness <name> models: lists its models`, or `cannot list models; a model becomes eligible after it has run once`, with the reason.

## Models found gone

An owned worker reads its harness's stream for one signal that the model it asked for does not exist here, or that this sign-in cannot use it. Jevris does not decide what a signal means. It looks the signal up in the router's table of signals and reasons. When the answer is a reason, the run ends with status `model-unavailable` (`MODEL_GONE` or `MODEL_NOT_ACCESSIBLE`, the harness and the sign-in mode). The task is not marked failed, and the model is recorded as found gone on this machine; see [routing.md](../routing.md#models-found-gone-on-this-machine). The harness's own message is never kept. Jevris keeps only the signal id and the key names of the event that carried it.

| Harness | Signal | Kind | Counts |
| --- | --- | --- | --- |
| Claude Code | `selected-model-issue`: a result with `is_error` and the "issue with the selected model" text | text-matched | only on a binary whose capture saw it, at that version |
| Codex | `model-not-found`, `model-not-supported-for-account`: a `turn.failed` or `error` message | text-matched | only on a binary whose capture saw it, at that version |
| OpenCode, Kilo | `provider-model-not-found`: an error named `ProviderModelNotFoundError` | structured | always, as `MODEL_NOT_ACCESSIBLE` for that harness and sign-in: it can come from the harness's own provider configuration, so it never hides the model on another harness. It is accepted both as the stream's error event and on stderr. Until a capture shows which channel it uses, `jevris certify` marks it unverified. |
| Antigravity | `unknown-model`: an `ERROR` result naming an unknown model | text-matched | only on a binary whose capture saw it, at that version, as `MODEL_NOT_ACCESSIBLE` (its model list depends on the plan) |

Until then a text-matched signal is reported in the run's outcome (`modelSignal`), but it never ends the run as `model-unavailable`. `jevris certify` prints one line per signal saying whether it counts on the installed version, and what the capture would launch.

**The capture** is a separate command, `jevris certify --harness <name|all> --model-signals`, and it runs only when you ask for it. For each harness it launches one headless turn on your own installed harness, with your own sign-in and settings. It runs in an empty temporary folder, with no tools and the prompt `Reply with OK.` on stdin, asking for a model id that does not exist. The exact command is printed before each run:

| Harness | What the capture launches |
| --- | --- |
| Claude Code | `claude -p --output-format stream-json --verbose --model claude-nonexistent-0 --max-turns 1 --max-budget-usd 0.05 ...` |
| Codex | `codex exec --json --model gpt-nonexistent-0 --sandbox read-only ...` |
| OpenCode | `opencode run --format json --model openai/gpt-nonexistent-0 --agent jevris-worker ...` (every tool denied, one step) |
| Kilo | `kilo run --format json --model openai/gpt-nonexistent-0 --agent jevris-worker ...` (every tool denied, one step, `KILO_NO_DAEMON=1`) |
| Antigravity | `agy --input-format stream-json --output-format stream-json --model gemini-nonexistent-0 --sandbox ...` |

The capture records the signal the harness showed, at its version, in `<data>/certifications/model-signals/<harness>.json`. A harness should refuse an unknown model before any billed work, but that is not guaranteed, so nothing runs the capture for you: not install, not a plain `jevris certify`, and not the test suite. In a test run it is refused unless `JEVRIS_LIVE_HARNESS=1` is set. A capture at one version certifies nothing at another version. After a harness upgrade, run the capture again.

## Certification

`jevris certify --harness <name>` runs the real harness binary in a throwaway profile. `jevris install` runs it after it installs. It writes one signed record per harness and operating system, `<data>/certifications/<harness>-<os>.json`. A record certifies a feature for a harness only when all of these hold:

- **The harness version is in the record's range.** The range runs from the version certified up to the next minor version, not including it. The rule is `same-minor` for all five harnesses, and it is set in each `plugins/<harness>/harness.json`. A patch release stays covered. A new minor version is re-checked in the background.
- **The operating system is the one it ran on.** A macOS record says nothing about Linux or Windows.
- **The record is less than 30 days old.**
- **That feature passed.** A feature that failed is recorded as unsupported. A malformed live event demotes its feature until a newer record exists.
- **The record has the feature at all.** A record written before a feature existed (`worker.route`, and `models.list` for every harness but Claude Code) is re-checked once in the background, with no model call, and until then that feature waits.
- **The signature verifies against a trusted key.** There are two kinds:
  - **Local:** the key `jevris certify` makes in `<data>/certifications/keys/`. A local record certifies that machine only. It is what `jevris doctor`, the hooks and owned-worker routing use there.
  - **Release:** a key with the `certification` role in the shipped `assets/trust/release-keys.json`, on a record that names the commit of a clean build. Only these count for the release gates. [platform-support.md](../platform-support.md) lists the combinations that hold such a record.

Kilo and OpenCode records carry two serving-host features as well. Neither fails the harness when it is not certified:

- **`models.list-hosts`:** the listing keeps each pinned serving host's own spellings. It needs the `<harness>.models-list-hosts` case. It is separate from `models.list`, so a listing side effect does not demote it, and it does not demote the listing.
- **`route.host`:** a route that changes the session's serving host, or any route through a gateway or third-party host, reaches that host, and a project config that redefines the host refuses it. It needs the `<harness>.session-route-host` and `<harness>.session-route-host-redefined` cases, and `session.route` certified in the same run (otherwise `ROUTE_HOST_NEEDS_SESSION_ROUTE`). A same-maker route through the session's direct maker host needs only `session.route` or `hooks.route`.

The cases run against the loopback stub with the dummy key, so nothing is billed. The two `session-route-host` cases check the plugin's project config guard on the folder the harness gave the probe plugin. The `-redefined` case passes on the guard's refusal alone, and notes whether the harness itself sent the turn to the project's redefined provider ([kilocode.md](kilocode.md), [opencode.md](opencode.md)).

### Access limits

Claude Code, Codex, Kilo and OpenCode records also carry the access-limit features, and Codex records also carry `access.usage-read`. None of them fails the harness when it is not certified. What each harness notices when an account runs out, per sign-in, is in [routing.md](../routing.md#what-jevris-notices-when-you-run-out). In this release:

- Kilo and OpenCode session events are always installed, so a session limit is read with or without `access.session`.
- Claude Code reads a session limit only once `access.session` is certified, because `StopFailure` is registered only then (below).
- Antigravity reads a session limit from a `Stop` that ended on an error (`terminationReason` `error`, marked with the fixed flag `errored`), through its pinned text patterns only. It has no certify case.
- Codex sessions are not read: no Codex hook event carries a failed turn's error.
- On a ChatGPT sign-in, the Codex model listing's usage read sets a timed pause when a window is used up. It lifts one only once `access.usage-read` is certified for the running Codex version.
- Owned runs through the harness CLIs end as `access-limit` (or `overloaded`) and record a pause, read by the port readers that `access.detect` checks. The Claude Agent SDK worker on an API key records its limits the same way.
- When it classifies a signal, Jevris reads these certifications from the signed record at the running version (`access.detect` for an owned run, `access.session` for a session). A credit or blocked-account error known only from a text pattern pauses with no expiry only on a certified channel; otherwise it is held as a timed pause.

The three features:

- **`access.detect`:** an owned run's port reads a rate limit, a credit error and a sign-in error from the harness's own error channel, and core gives each its class. It needs the `<harness>.access-limit.rate`, `<harness>.access-limit.credit` and `<harness>.access-limit.auth` cases. In each, the stub answers every model request with that error in the API's own shape. Claude Code retries a 429 and a 401 itself, so its cases run with `CLAUDE_CODE_MAX_RETRIES=1` and without `CLAUDE_CODE_RETRY_WATCHDOG`, as Codex's set the provider's retries to 0. Antigravity has no custom endpoint, so it has no case.
- **`access.session`:** an interactive session's failed turn reaches the hooks with a structured error. For Claude Code that is `StopFailure` (`claude.session.stop-failure`), whose documented `error` field must be `billing_error` on the scripted 402; the hook reads that `error` and a pinned pattern from `error_details` or `last_assistant_message`, never their text. For Kilo and OpenCode it is `session.error` or a failed assistant message (`<harness>.session.error`); the hook takes a rate limit's reset from the response headers (`retry-after` and the known reset headers). It needs `hooks.observe` (otherwise `ACCESS_SESSION_NEEDS_HOOKS`). A binary that never sends the event records `ACCESS_SESSION_EVENT_ABSENT`: a documented unsupported feature, not a failure. No Codex hook event carries a failed turn, so Codex sessions are not read. Antigravity has no `access.session` case: its error `Stop` is read through pinned text patterns and is never certified. The Claude Code plugin does not list `StopFailure`: `jevris install` registers it, exactly as `Stop` is registered, only once a record certifies `access.session` for the installed binary. When the certify step of an install certifies it for the first time, the install registers it in the same run and prints `claude hooks: StopFailure registered (certified in this run)`. `jevris doctor` compares the installed `hooks.json` with the record for the installed binary. If `StopFailure` is registered but `access.session` is no longer certified there (a new binary or a demotion), it prints the action `harness claude install: StopFailure registered, but access.session is not certified for <version>; fix: jevris install --harness claude`, and that install renders the plugin again without it. If `access.session` is certified but `StopFailure` is not registered yet (a `jevris certify` run outside install), it prints the information line `harness claude hooks: StopFailure not registered yet, ...; to add: jevris install --harness claude`.
- **`access.usage-read`** (Codex only): the model listing's `account/rateLimits/read` answers with the fields core keeps, and nothing leaves the machine while it does (`codex.usage-read`). The case runs `codex app-server` against the stub with a dummy ChatGPT login in a throwaway folder, under the operating system's network isolation: on macOS `sandbox-exec` with a profile that allows only the stub's loopback port and denies the name-resolving services, on Linux an unprivileged user and network namespace with only `lo`. From inside, it first checks that an outbound connect is refused and a name does not resolve. It passes only when every request reached the stub alone and the answer parses to exactly the stub's windows. On Windows, or where the isolation cannot start, it records `ACCESS_USAGE_ISOLATION_UNAVAILABLE`: a documented unsupported feature, and nothing runs unisolated.

Every scripted error body and header carries a canary. A case fails if the canary reaches a signal, a finding, a normalized event or the case's own result. Each case runs under a fixed 60-second bound, and a run still going at the bound fails (`HARNESS_KEPT_RETRYING`); a timeout is never a pass.

The reasons a record gives when an access feature is not certified:

| Reason | Meaning |
| --- | --- |
| `ACCESS_DETECT_CASE_FAILED` | One of the three `access-limit` cases ran and failed; the detail names the case and its reason. |
| `ACCESS_DETECT_CASE_NOT_RUN` | One of the three `access-limit` cases did not run. |
| `ACCESS_SESSION_NEEDS_HOOKS` | `hooks.observe` did not pass in the same run. |
| `ACCESS_SESSION_EVENT_ABSENT` | The probe ran and the turn ended on the scripted error, but the binary never sent the event. A documented unsupported feature. |
| `ACCESS_SESSION_CASE_FAILED` | The `session.stop-failure` or `session.error` case ran and failed for any other reason, including a probe that never ran and a turn that never reached the error. |
| `ACCESS_SESSION_CASE_NOT_RUN` | The `session.stop-failure` or `session.error` case did not run. |
| `ACCESS_USAGE_ISOLATION_UNAVAILABLE` | No OS network isolation here (Windows, or `sandbox-exec`, `unshare` or user namespaces not available), so `codex.usage-read` did not run. A documented unsupported feature; the release gate accepts it on Windows only. |
| `ACCESS_USAGE_CASE_FAILED` | `codex.usage-read` ran and failed, including a failed isolation check inside. |
| `ACCESS_USAGE_CASE_NOT_RUN` | `codex.usage-read` did not run. |

### Where things stand

[platform-support.md](../platform-support.md) lists every harness, version and operating system combination that holds a release record, generated from the signed records in `release-evidence/`. Windows has no release record yet; see [Windows](#windows). On your own machine, `jevris doctor` prints each local record and its version range.

## How to read it on your machine

`jevris doctor` prints four kinds of line.

**Harness line**, one per harness:
- `certified for <version range> (last verified <version>, <date>): <features>` when a signed record covers the harness version and operating system here.
- `not certified: no signed record covers this version on this host; fix: jevris certify --harness <name>` when none does.
- `not covered yet: <version> is outside the record covers <range> (...); re-checking in the background, no model call` after the harness updates past the range its `harness.json` declares (`compatibility`, same-minor for all five today). The check is `jevris certify` in a throwaway profile, run at most once per version; a pass extends the certification, and a failure names the failing feature with its fix.
- `...; not certified here: <feature> (<reason>)` when a check failed for one feature, or a malformed live event demoted it (`LIVE_EVENT_MALFORMED`). Only that feature waits; observation and advice go on.
- `...; optional, not certified here: access.detect (<reason>), access.session (<reason>), access.usage-read (<reason>)` for the access-limit features. They carry no fix, and this clause alone does not make the line an action. What still works without them depends on the harness ([Access limits](#access-limits)): without `access.session`, Claude Code reads nothing from a session (its `StopFailure` hook is registered only once the feature is certified), Kilo and OpenCode still read `session.error`, Antigravity still reads its error `Stop` through uncertified patterns, and Codex has no session event. Without `access.detect`, an owned run's port reads a limit either way, but its class is not proven for that binary. Without `access.usage-read`, a Codex usage reading still sets a timed pause but never lifts one.

**Worker line**, one per harness with a record: whether route learning may choose an owned worker's model and effort there (`worker.route`, "certified pending first use"). In 1.2 it does not decide whether a submitted task's worker starts: that worker starts on its approved model either way. Certify checks the worker port against a stand-in, not your installed harness, so the exact worker launch is first proved by the first real run ([routing.md](../routing.md#what-certification-covers-for-owned-workers-in-12)). It reads `certified, pending first use`, `verified in use (N runs at <version>)`, `demoted: an owned run's first-use check failed; ...`, `not certified here (<reason>)` or `not certified yet: the record for <version> predates owned-worker certification`. A record written before `worker.route` existed (such as the Certify row's records above) starts one background re-check. On a harness not certified for `worker.route`, route learning only advises (`ACTUATOR_UNCERTIFIED`): the task runs on its approved model at the model's default effort. See [routing.md](../routing.md#certification-of-worker-routing).

**Models line**, one per installed harness: `harness <name> models: lists its models (...)` when `models.list` is certified and `routing.modelListing` is on, or `cannot list models; a model becomes eligible after it has run once`, with the reason ([Model listing](#model-listing)). Information, not a problem.

**Eligibility line**, one per installed harness and the sign-in its owned workers use: `harness <name> eligibility (<sign-in> sign-in): eligible: <models>; not eligible: <reason> <count>, ...`. A model is eligible there once it has run on that harness and sign-in, or once the harness lists it and the registry's harness map gives the harness its provider. A model found gone never is. On a fresh install the line reads `no model is eligible yet`, which means routing cannot choose a model there yet. With `--harness`, the line for each model follows. When an administrator's registry has account checks, those decide, and the line says so without printing the account. Information, not a problem.

**Parity line**, one per harness: `harness <name> parity: not available in <name>, by design: <feature> (<reason>); ...` (information, not a problem). Codex adds `harness codex hookTrust: ...`, the one step you take in Codex (`/hooks`).

**Actuator line**: a feature that is implemented but not certified on this host stays in observe mode. Hooks never make a permission decision.
