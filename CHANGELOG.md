# Changelog

Versions follow [semantic versioning](https://semver.org). Releases are published to npm as [`@webventures/jevris`](https://www.npmjs.com/package/@webventures/jevris) under the `next` tag and promoted to `latest` only when every release gate passes on evidence (see [RELEASING.md](RELEASING.md)). The `v1.0` and `v1.1` entries are milestones of the private workspace; `1.2.0` is the first published version.

## 1.2.0

The first public release: one package that installs into five coding harnesses on macOS, Linux and Windows.

### Install and platforms

- Published as `@webventures/jevris`. `npx @webventures/jevris` and `npm i -g` work without a clone, a build or a compiler, on Node `^22.14.0 || >=23.6.0` (Node-API 10). Older Node exits with one plain line.
- One bundled package: every workspace is bundled into `dist/`; the only runtime dependencies are `better-sqlite3`, `@napi-rs/keyring` and `@typesafe-ai/sdk`. The Claude Agent SDK is an optional peer. An SBOM, third-party notices and `SHA256SUMS` ship with each release, which is published with npm provenance.
- `install` covers Claude Code, Kilocode, Codex, OpenCode and Antigravity (Gemini CLI support is retired). It copies a versioned runtime to the Jevris data folder and points every harness there, never at the npm cache. `--dry-run` prints every change; `--yes` applies it; on a terminal install asks before it applies, and without a terminal or `--yes` it prints the plan, changes nothing and exits 0. After a successful install it certifies each harness it installed, with no model call (`--no-certify` skips this); a harness that does not certify never fails the install, and its `certify` line names the fix. Install detects each harness's sign-in mode, asks once on a terminal for one it cannot detect (recorded in `workers.json`), and lists only the steps left to you: restarting Claude Code and trusting the hooks in Codex. Every changed file is backed up and restored on failure, and other tools' settings in shared config files are kept byte for byte.
- Install writes no settings file, so a fresh install runs on the defaults: mode `bounded-auto`, with orchestration and owned workers on.
- `uninstall` removes only what Jevris added, with `--keep-data` (default) or `--delete-data`. `data delete` is separate.
- Per-OS folders: XDG on Linux, `%APPDATA%` and `%LOCALAPPDATA%` on Windows, `~/.config/jevris` and `~/.jevris` on macOS. `--home` is optional everywhere (default `JEVRIS_HOME`, then your home). Private files are owner-only on every OS.
- `jevris --help`, `jevris help <command>` and `--version`.

### Mode and authority

- `mode` is the single ceiling on what Jevris does, and the default is `bounded-auto`. `off` does nothing: hooks are a no-op, nothing is recorded and Jev is not asked. `observe` records facts and asks Jev for a counterfactual that is recorded but never shown. `advise` also shows advice, including the one Stop continuation. `bounded-auto` also acts on certified capabilities. `routing.managedWorkers`, `routing.mainSession` and `orchestration.enabled` only narrow the mode. `host.json`, `organization.json` and a managed policy cap it, the lowest wins, and `configure`, `status` and `doctor` name the layer that set it. Each decision record names the mode it was made under. See [settings.md](docs/settings.md#modes).
- In `off`, Jevris makes no Jev call and no background network call. `route`, `plan`, `recover`, `advise` (CLI and MCP) and `credential reenable` are refused with `MODE_OFF` and the command that turns Jevris back on. Read-only commands keep working. The sidecar skips the harness model listing (with Codex's usage read) and the certification re-check.
- A `jevris.config.json` that is present but unreadable, not JSON or not matching the contract caps the mode at `observe`, and shows a `user:` issue in `configure`, `status` and `doctor`. `jevris configure set mode off` (or `observe`) moves it aside to `jevris.config.json.invalid` and writes a fresh one. The unusable file stays in place until the fresh one is written, so the cap holds on every failure (`CONFIG_DIR_REFUSED`, `CONFIG_WRITE_FAILED`). A missing file means the defaults. An administrator policy file that cannot be used, and a refused managed policy, also cap the mode at `observe`.
- A file an earlier build's `configure set` wrote says `"mode": "observe"` even if you never chose it. Once per home, the sidecar at start (or the first `configure set`) moves such a file to `bounded-auto` and keeps every other key; `status` and `doctor` say so in one line until you run `jevris configure set mode`, or for 30 days. To stay in observe, run `jevris configure set mode observe`.
- Changes that widen what Jevris may do need a person at an interactive terminal who answers `y`. `--yes`, `--json`, a pipe, a script, MCP, a hook and a test run are refused with `CHANNEL_REFUSED`, and nothing changes. This covers a `configure set` that raises `mode`, `routing.managedWorkers` or `routing.mainSession`; `verify approve`, `verify issuer add` and `verify waive`; `configure owned-mode on`; `pack approve` and `pack publisher add`; and `plan --submit` with a new root budget, which also takes a single-use `--authorization` from `jevris authorize`. Lowering needs no one. See [security.md](docs/security.md#changes-that-need-a-person-at-a-terminal).
- An egress approval in `host.json` counts only from a regular file you own that no one else can write, with neither it nor the Jevris home inside a git work tree.

### Runtime

- A local, authenticated sidecar (Unix socket, or a per-user named pipe on Windows) that commands start on demand: `jevris sidecar start|stop|restart|status`.
- A hook launcher per harness that answers within the harness's hook deadline, falling back to "observe" whenever the sidecar is down, late or refuses. A harness retry of the same event within 5 minutes gets the first answer again, unchanged (`DUPLICATE_REPLAYED`), so nothing is spent or applied twice.
- An MCP server with 17 tools, among them the eight public ones (`status`, `plan`, `route`, `checkpoint`, `recover`, `verify`, `explain`, `configure`), and matching skills in every harness.
- A versioned SQLite store with migrations, backups before destructive steps, and refusal of a newer schema.
- The Jev key in the OS keychain (`jevris credential set|clear|status`), read from standard input only, and used only by the sidecar.
- A persisted decision engine: bounded questions, budgets and reservations, caching, and certification-gated actuation.
- Task graphs, leases and verification receipts for orchestration; completion only from independent evidence.
- The kill switch, host and organization policy, and settings (`jevris configure`) that never touch native harness permissions.
- Managed policy and a managed kill switch from admin-owned locations (`/Library/Application Support/Jevris/`, `/etc/jevris/`, `%ProgramData%\Jevris\` or `HKLM\Software\Policies\Jevris`). On macOS and Linux a file (or a folder above it) that is not root-owned, or that a group or other users can write, is refused; on Windows only SYSTEM, Administrators and TrustedInstaller may write it. A refused policy approves nothing, and a refused kill switch counts as stopped.
- An opt-in Jev key source for headless Linux, CI and WSL: an owner-only file (`JEVRIS_CREDENTIAL_FILE`) or a systemd credential (`JEVRIS_CREDENTIAL_SYSTEMD`). The keychain stays the default, and Jevris never searches for a key.
- Retention: raw artifacts 7 days and redacted decisions 30 days by default. Route learning is its own retention class, removed only by `jevris route learning reset --clear-evidence` or `jevris data delete`. The access-limit record and the Codex usage readings are in that class too, and `jevris data delete` and `uninstall --delete-data` remove them.
- `JEVRIS_SIDECAR_AUTOSTART=0` stops every surface from starting the sidecar. Hook subscribers get at most 700 ms each (`SUBSCRIBER_QUEUED` past that); a SessionStart restore, a Stop reminder and a PreCompact capsule are never answered BUSY under load; stale sockets and locks are recovered; the sidecar exits after 30 idle minutes, or runs as a per-user service with `jevris service` (a LaunchAgent, a systemd user unit or a Scheduled Task).
- `jevris sidecar metrics`, `statusline` and `diagnose`, and local traces that hold ids, codes and counts, never content.

### Jev provider

- Each Jev call ends at its deadline end to end. The transport owns the total deadline: connect, headers and the body read all stop at it, even when the network, the SDK or a gateway client ignores its abort signal. A late call is `DEADLINE` and a caller abort stays `CANCELLED`. The conformance fixtures include a stalled body (`late-body`) and a provider that never answers (`late-deaf`).
- The Jev circuit stays open for the provider's `Retry-After`, at most 15 minutes. A billing failure (402) or a forbidden account (403) turns Jev calls off until `jevris credential reenable`, which a person runs at a terminal once the cause is fixed; it calls nothing. A refused key (401) clears only with a new key. `status` and `doctor` show why Jev is off.
- The live Jev suite (`JEVRIS_LIVE_JEV=1 npm run smoke:jev`) measures under a 10 s timeout instead of cutting calls off. Its evidence record keeps every latency call's elapsed milliseconds and outcome, counts failed calls per reason code, and gives p50, p95, p99, max, the share of calls within the 900 ms hot budget and whether p95 meets the 800 ms target. Numbers and codes only; no body or remote text fits. The product's hot path keeps its 900 ms budget.

### Harnesses and certification

- One plugin source for all five harnesses (`plugins/shared` plus each harness's manifests); install renders each harness's files, and nothing generated is tracked.
- `jevris certify --harness <name|all>` certifies a harness in a temporary profile with no model call. Where a feature needs a model turn, Claude Code, Codex, Kilo and OpenCode in the throwaway profile are pointed at a local stub provider with a dummy key. A record covers a harness version range (`compatibility` in each `harness.json`); a version outside it is re-checked in the background, at most once per version, so routine harness upgrades need no manual re-certification. `jevris doctor`, the sidecar's start and each SessionStart start the re-check.
- Certification features: `plugin.install`, `mcp.tools`, `skills.discovery`, `hooks.observe`, `hooks.context`, `hooks.route`, `worker.route`, `models.list`, `worker.actual-model`, `session.route`, `models.list-hosts`, `route.host`, `access.detect`, `access.session` and `access.usage-read`. The stub cases cover subagent routes (K1–K4), the owned run's reported model (K8), serving hosts on Kilo and OpenCode (K13–K15), access limits (K16–K20) and the Codex usage read under OS network isolation (K21). The harness-conformance evidence names each stub case's id, whether it passed and its reason code.
- Live certification evidence: the sidecar records each hook delivery, and each owned worker its first-use check, as conforming or malformed for one feature and harness version. A malformed one demotes that feature at once and starts a background re-check.
- Claude Code's `StopFailure` hook is registered only once a record certifies `access.session` for the installed binary; doctor says when the two disagree.
- Doctor marks each line `✓`, `i`, `!` or `✗`, names a fix for every problem, shows the effective mode and the layer that set it, each harness's sign-in mode and `certified for <range> (last verified <version>, <date>)`, and `doctor --json` adds `summary`, `lines` (each with its severity) and `privateFiles`.
- Owned-worker ports: Claude Code (`claude -p`, or the Claude Agent SDK with an API key only), Codex (`codex exec --json`), OpenCode (`opencode run`), Kilo (`kilo run`) and the Antigravity CLI (`agy`) all run owned workers. A refused run whose first-use check failed leads its reason with the code (for example `WORKER_INIT_MODEL`). A run the port refused before any child started releases its reservation (`LAUNCH_NOT_STARTED`).
- `worker.route` (owned workers) is a certification feature, "certified pending first use": `jevris certify` checks that each harness's help lists every flag its worker passes (`WORKER_FLAG_MISSING` otherwise) and runs the nine conformance cases against each worker port, with no model call. The first real run checks its init before any tool runs; a Claude Code or Antigravity mismatch stops the run, and any failed check demotes the feature. Doctor's worker line reads `certified, pending first use`, `verified in use (N runs at <version>)`, `demoted` or not certified with the fix.

### Routing, learning and owned workers

- Opus 5.5 is the default and baseline model on Claude Code (1M context, 128K output, default effort `medium`). Codex's baseline is GPT-6 Sol and Antigravity's is Gemini 3.8 Flash.
- The bundled registry snapshot `multi-2026-09-28` lists seven providers: Anthropic (Opus 5.5, Fable 5.1, Opus 5, Sonnet 5, Haiku 4.5), OpenAI (GPT-6 Astra, Sol and Luna; GPT-5.6 Sol, Terra and Luna), Google (Gemini 3.8 Flash, 3.7 Flash, 3.1 Pro preview), xAI (Grok 4.7, 4.6), Z.ai (GLM-5.3), Moonshot (Kimi K3) and DeepSeek (V4 Pro, Flash). The non-Anthropic models are unevaluated. Prices carry an integer micro-USD form, long-context tiers, announced price changes and promotion ends. The harness map records how each harness spells a model and takes effort. `npm run registry:check` validates the registries. See [routing.md](docs/routing.md).
- Consent per model provider: `jevris consent provider` lists, grants and revokes it. Moonshot and DeepSeek always need a grant, and their models are eliminated with gate `provider-consent` until then; another provider is allowed while you are signed in to it on an installed harness. A preview model never enters an automated route (gate `preview`). A model becomes eligible on a harness only from local evidence: it ran there, or the harness lists it.
- Serving hosts: the snapshot records which models OpenRouter, the Kilo Gateway and NVIDIA serve on Kilo and OpenCode, at the host's tariff where it is known. A route keeps the session's host. A route through a host needs consent for the host and the maker; NVIDIA has no consent text, so Jevris never routes to it. A route that changes host or goes through one is advice until `route.host` is certified, and Jevris acts only when both models' prices on their hosts are known.
- Subagent routes: Jevris may propose a subagent's model on Claude Code, Codex, Kilo and OpenCode, each only after that harness's `hooks.route` is certified, and never over an explicit model or a pin. Codex subagent routing is advice only unless its certify case passes on the installed Codex version. Antigravity gets the advice as text. Jevris proposes only with evidence for that subagent type (an active learned slice or a signed prior); subagent outcomes do not feed learning yet and 1.2.0 ships no signed prior, so in practice it abstains and the subagent keeps the harness's choice.
- Main-session turns on Kilo and OpenCode: with `routing.mainSession` at `plugin-bounded-auto` (the default), a turn's model may be switched once `session.route` is certified, only for a session linked to a low-risk task (`jevris route --task <id> --link`, or `jevris handoff import <capsule.json> --link`). Every other main session is advice only.
- Access limits: when a run or a session hits a rate limit, a usage window, exhausted credit or a blocked account, Jevris pauses that account on this machine and keeps routing and owned workers away from it until it recharges. It never spends a call to test a pause. A blocked task resumes once per episode when its wait is over. `jevris route limits` lists the pauses, and `jevris route limits clear` (a person at a terminal) removes them; `status` and `doctor` show them. On a ChatGPT sign-in the Codex model listing also reads the remaining usage once, read-only; a reading lifts a pause only where `access.usage-read` is certified. See [routing.md](docs/routing.md#access-limits-when-an-account-runs-out).
- Each harness runs on a subscription login or an API key, both first-class, stated per harness in `workers.json` (`jevris-workers-1`) or detected. Costs follow the mode: dollars on a key, usage-limit consumption with a labelled API-equivalent estimate on a subscription. Claude models in OpenCode or Kilo need an Anthropic API key. Grok models run in OpenCode or Kilo on the harness's own SuperGrok login or on `XAI_API_KEY` (`XAI_API_KEY_MISSING`, `XAI_PLAN_NOT_ELIGIBLE`, `XAI_AUTH_FAILED` name the failures). Antigravity runs only on its Google sign-in. Doctor detects the mode: `claude auth status`, `codex login status`, `opencode auth list` and `kilo auth list` (credential types only, never values).
- Route learning for owned workers: a per-workspace Bayesian posterior learns from verified outcomes with the owner-locked thresholds. Arms are a model at an effort level (Opus 5.5 at low, medium and high). 1.2.0 ships no signed baseline release: every slice starts on its baseline at its default effort and switches only after 12 of the workspace's own randomized outcomes on each arm. A later release may ship a signed baseline at `assets/calibration/calibration-release.json`, and a `calibration-release.json` in the config folder overrides it. `jevris route learning` shows it and turns it off, pins a slice (`--effort`, `--advise`), resets, rolls back, switches between automatic and review, lists models found gone on this machine (`gone`) and exports local calibration cases (`export-cases`); `jevris explain --slice` and `trace.learning` explain it. Routing acts only on a harness certified for `worker.route`; elsewhere it advises (`ACTUATOR_UNCERTIFIED`) and the approved model runs at its default effort. The routed effort reaches the harness (`--effort`, `model_reasoning_effort` or `--variant`), the run record and the learning event; the Agent SDK takes none.
- A model stays recommended until it is actually retired. One found gone on this machine is never routed, explored or launched again.
- Owned work: `jevris plan --submit`, owned mode per workspace (`jevris configure owned-mode`), `jevris task`, `jevris budget`, `jevris integrate`, and the multi-host control service (`jevris control`).
- Advice and reports: `jevris advise`, `jevris delivery`, `jevris cost-report`, `jevris feedback` (accept or reject a decision's advice, with a reason), `jevris handoff import`, and the MCP tools `jevris_advise`, `jevris_delivery_report`, `jevris_handoff_export` and `jevris_handoff_import`.
- Policy packs with a draft, fixture-tested, shadow-approved, canary and stable lifecycle (`jevris pack`).

### Terminal output

- Colour, text styling and the Jevris logo in a terminal (on `--help`, `--version`, `doctor` and `install`). A pipe, a file, `--json`, `--no-color`, `NO_COLOR`, `TERM=dumb` and `FORCE_COLOR=0` give plain text with the same words.

### Release engineering

- CI on macOS, Linux and Windows with Node 22.14.0, 24 and the current release, plus an installed-package smoke test per OS.
- `jevris gates` judges eight release gates (API, harness, security, quality, economics, operations, portability and perf) from signed, schema-validated evidence. With no seed run for 1.2, the quality gate requires the run-time learning gate's named tests (the locked thresholds, fast demotion, pins, learning off and capped exploration) to pass in the release run, and the economics gate the tests of in-use reporting (cost and time per verified task against the default in explain and status, and reversion) and of independent pack disable; `node scripts/acceptance-report.mjs` records them in `runtime-gate-report.json`. When a package ships a signed baseline release, the quality gate also checks it and its seed, and a seed economics record is still judged when present; there is no large offline trial. For every harness with `worker.route`, the harness gate needs the nine worker conformance cases (`harness.<h>.worker.<os>`) and the portability gate a published record with `worker.route` certified (`portability.worker-route.<h>.<os>`). A harness advertised with routing also needs its route and access features certified, except Codex subagent routing, which 1.2 does not require. Certify's release evidence names the commit of a clean build.
- The API gate reads the live suite's record: `api.error-taxonomy` counts only probes the provider answered with their expected code, `api.latency-sample` needs every latency call to succeed, and `api.latency-envelope` fails when the envelope is unknown and prints WARN outside the 800 ms and 900 ms targets. The targets are unmeasured engineering targets, so the release owner decides.
- The perf gate reads `npm run bench:load` on the reference machine: 13 locked sidecar load targets under 20 and 50 concurrent subagents.
- A model the router still recommends that may retire within 30 days, or is deprecated, is a release WARN and a `registry:check` warning; the gate fails only on release data that contradicts itself. [docs/model-refresh.md](docs/model-refresh.md) is the refresh procedure.
- A tag-driven release workflow with provenance, a post-publish check on three operating systems, and promotion to `latest` only through the gates.
- Seeded property, crash-point, race and fuzz suites; no wall-clock windows under 2 s and no negative-lock tests.
- Acceptance tests for all 40 user stories and 12 workflows of the specification, and an installed-package smoke that ends with the doctor proof: install, `certify --harness all`, then `doctor --json` must read full, certified and passed.
- The build, lints and tests read only the repository: the specification's examples, schemas, user stories and reference suite are in `fixtures/ssot/`, and the model and cost registry proposals in `fixtures/registry/`.
- Test isolation: a temporary home and temp folder per run with guards that fail on any leak, stub harness binaries, a blocked keychain and a tripwire that refuses to start a real harness binary. `npm run verify:fresh` runs the CI steps on a fresh clone, and `npm run test:future` runs the suite days ahead. `scripts/safe-commit.mjs` and the suite locks serve checkouts that several people or agents commit to.

## v1.1 (milestone, 2026-09-25)

Full delivery programme in the private workspace; not published.

- Host secret broker, administrator policy outside the workspace, and a local refusal of source-bearing checks without consent.
- A transactional SQLite store for decisions, proposed actions and the outbox.
- A Unix-socket sidecar that authenticates callers before any source read, and a command hook that exits cleanly with no decision on a missed deadline, a down sidecar or invalid input.
- Checkpoint, status and advice over the sidecar; the kill switch and its drill record.
- Owned Claude sessions, fenced task leases, integer budget reservations and runner-bound verification receipts.
- A Claude plugin with a closed-graph hook bundle. Every actuator stayed uncertified and the release gates stayed not-a-pass.

## v1.0 (milestone, 2026-09-23)

Observe and advise, in the private workspace; not published.

- Rules-only path, egress gate, and credential absence that does not search for another provider.
- Claude install copy, uninstall, and data delete. Installed is not enforced.
- Doctor report for harness version, egress, environment class and unsupported actuators.
- Checkpoint allow on compact, with no replacement summary.
- Skill and evidence shortlist that does not execute skills or upload a repository.
- Shadow comparison that records rules-only, native and Jev labels with actuation count 0.
- TypeSafe provider package pinned to `@typesafe-ai/sdk@0.6.0`.
